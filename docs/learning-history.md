[Проектный план и архитектура первой демонстрации](project-plan.md) связывают существующее игровое ядро с будущим запускаемым сценарием для двух игроков. В документе отдельно указаны готовые части и еще не реализованные интеграции.

Учебная реализация заданий OTUS. Занятия 7-9 добавили движение, поворот, очередь, обработку ошибок и макрокоманды. Занятие 11 добавило IoC, занятие 13 - генерацию адаптеров, занятие 17 - параллельных работников с собственными очередями. Прежние `Move`, `Rotate` и рабочий цикл очереди сохранены. Для ДЗ занятия 23 подготовлена [целевая микросервисная архитектура](microservices.md). Документ показывает границы сервисов, API, потоки сообщений, масштабирование и места расширения. Описанные сервисы пока не реализованы; текущий пакет остается ядром исполнения игры.

ДЗ занятия 25 добавляет [сервис авторизации и защищенный игровой endpoint](auth-service.md): зарегистрированные участники получают JWT для конкретной игры, а команда принимается только с действительным токеном владельца корабля. Прежний Go-код и локальный конструктор endpoint сохранены.

ДЗ занятия 27 добавило [смену режимов работника](worker-states.md). ДЗ занятия 28 добавляет [индекс окрестностей для проверки коллизий](collision-neighborhoods.md): он собирает возможные пары из нескольких смещенных сеток, а точную проверку столкновения получает извне.

## Запуск

Из каталога проекта:

```sh
go build ./...
go test ./...
go vet ./...
```

### Локальная демонстрация проекта

```sh
go run ./cmd/battle-demo
```

Демо слушает только `127.0.0.1:8096`. При запуске оно создает одну игру, ключ подписи токенов и временные пароли игроков `alice` и `bob`. Идентификатор игры и пароли печатаются в терминал; после остановки процесса они больше не действуют. Не используйте эти учетные данные вне локального демо.

Подставьте выведенные значения вместо `<game-id>` и `<password>`:

```sh
curl -u 'alice:<password>' -X POST 'http://127.0.0.1:8096/games/<game-id>/tokens'
```

Из ответа скопируйте `access_token` вместо `<token>`. Приказ `StartMove` устанавливает скорость, `Advance` делает один шаг корабля, `StopMove` останавливает его:

```sh
curl -X POST 'http://127.0.0.1:8096/commands' \
  -H 'Content-Type: application/json' -H 'Authorization: Bearer <token>' \
  -d '{"game_id":"<game-id>","object_id":"ship-alice","operation_id":"StartMove","args":{"initialVelocity":2}}'
curl -X POST 'http://127.0.0.1:8096/commands' \
  -H 'Content-Type: application/json' -H 'Authorization: Bearer <token>' \
  -d '{"game_id":"<game-id>","object_id":"ship-alice","operation_id":"Advance","args":{}}'
curl 'http://127.0.0.1:8096/state?game_id=<game-id>' -H 'Authorization: Bearer <token>'
```

Токен `bob` не может управлять `ship-alice`: сервер вернет `403`. Снимок читается через очередь того же игрового работника, поэтому показывает состояние после ранее принятых приказов. `202` пока не сообщает успех конкретной команды; подробное ограничение описано в [плане проекта](project-plan.md).

В CI выполняются те же проверки. Для JWT используется одна внешняя зависимость `github.com/golang-jwt/jwt/v5`; остальной код опирается на стандартную библиотеку Go.

Для изменений, затрагивающих параллельную работу, дополнительно выполняется `go test -race ./...`. Он запускается и в CI.

## Контракт

`Move{Object: object}.Execute()` читает положение и мгновенную скорость, складывает векторы и записывает новое положение. Операция не меняет скорость и не деформирует объект. Ошибка любого чтения или записи возвращается вызывающему коду с указанием этапа; исходная ошибка доступна через `errors.Is`. При ошибке чтения или нечисловом результате запись не вызывается.

`Rotate{Object: object}.Execute()` читает направление и угловую скорость, поворачивает на целое число секторов и записывает новое направление. Сектор нормализуется по кругу, включая отрицательные повороты. `Direction` создается через `NewDirection(index, sectors)` с `sectors > 0`. Нулевое значение `Direction` недопустимо.

В Go нет классов: отдельные операции оформлены структурами `Move` и `Rotate` с методом `Execute`. Интерфейсы `MovingObject` и `RotatingObject` содержат только операции, нужные соответствующей команде. `Ship` реализует оба интерфейса; `Torpedo` реализует только движение. Компилятор проверяет это через присваивания в конце файлов моделей.

`Ship` хранит не вектор скорости, а неотрицательную скалярную скорость и дискретное направление. Метод `Velocity()` вычисляет `speed * (cos(angle), sin(angle))`, где `angle = 2π * index / sectors`. Поэтому поворот влияет на следующий шаг движения. `Torpedo` хранит вектор скорости напрямую; код `Move` от этого не меняется.

Ограничения игрового поля можно разместить в `SetPosition` конкретного объекта или адаптера. Если новое положение запрещено, метод возвращает ошибку, а `Move` передает ее вызывающему коду. Тест `write position` проверяет этот путь. Это не реализует всю игровую механику: столкновения, победа флотилии, Player и Агент находятся за пределами задания на движение.

## Занятие 8: очередь и обработка ошибок

`Move` и `Rotate` теперь выполняются через общий интерфейс `Command`. `Processor` извлекает команды из FIFO-очереди и передает сбой первому подходящему `ErrorRule`, которое может учитывать и тип команды, и значение `error`. Обычные ошибки возвращаются как `error`; `panic` преобразуется в ошибку только на границе рабочего цикла. Если правило не найдено, ошибка возвращается вызывающему коду.

`LogFailure` пишет тип команды и сообщение ошибки в переданный `io.Writer`. `Retry` и `RetryTwice` выполняют исходную команду повторно. Обработчики `EnqueueLog` и `EnqueueRetry` только добавляют команды в очередь. `RetryOnceRules` дает одну повторную попытку и затем журнал; `RetryTwiceRules` дает две повторные попытки и затем журнал. Ошибка записи журнала не повторяется бесконечно. Тесты проверяют оба сценария, выбор по обернутой ошибке, FIFO, восстановление после `panic` и исполнение старой команды движения в новом цикле.

Повтор любой команды допустим здесь как требование ДЗ. Для реального сервера потребуются классификация временных ошибок и гарантия безопасного повторного выполнения после частичного действия. Очередь сейчас рассчитана на одного рабочего.

## Занятие 9: макрокоманды и топливо

`MacroCommand` принимает последовательность `Command`, исполняет ее по порядку и останавливается на первой ошибке. `CommandError` сохраняет номер неудачного шага и исходную причину через `Unwrap`, поэтому работают `errors.As` и `errors.Is`.

`NewMoveWithFuel` строит цепочку `CheckFuel -> Move -> BurnFuel`. Нехватка топлива останавливает движение. Ошибка `Move` не запускает списание. `BurnFuel` проверяет остаток и при отдельном вызове не допускает отрицательного запаса. `FueledShip` использует правила прежнего `Ship`, хранит запас топлива и собственный вектор скорости. При создании он копирует исходный `Ship`, чтобы дальнейшие изменения через старый указатель не нарушили его состояние.

`NewRotateWithVelocity` строит цепочку `Rotate -> ChangeVelocity`. `ChangeVelocity` обновляет вектор только у объекта с контрактом `VelocityAdjustable`. Для неподвижной поворачиваемой башни это допустимое пустое действие. Прежний `Ship` сам вычисляет вектор из направления, поэтому после поворота его скорость уже корректна. У `FueledShip` вектор хранится, и составная команда пересчитывает его явно.

Макрокоманда не выполняет откат. Если `BurnFuel` вернет ошибку, положение уже может быть изменено. Поэтому общие правила повтора из занятия 8 нельзя применять к ней без проверки безопасности повторного выполнения. В тестах проверены порядок шагов, остановка на ошибке, нехватка и точный остаток топлива, связь поворота со следующим движением, объект без движения и сохранение поведения прежнего `Ship`.

## Занятие 11: расширяемая фабрика и IoC

`NewIoC()` создает контейнер. Его единственный публичный метод `Resolve[T](session, key, args...) (T, error)` получает зависимость по ключу. Метод доступен благодаря Go 1.27, указанному в `go.mod`. Фабрика имеет тип `Factory`, получает аргументы вызова и возвращает `any, error`. Контейнер проверяет, что результат совместим с запрошенным `T`; неизвестный ключ, неверные аргументы и несовместимый тип дают отдельные ошибки.

Регистрация и управление областями тоже проходят через `Resolve[Command]`:

```go
func runMove(torpedo *Torpedo) error {
	ioc := NewIoC()
	session, err := NewScopeSession(ioc)
	if err != nil {
		return err
	}
	factory := Factory(func(args ...any) (any, error) {
		if len(args) != 1 {
			return nil, ErrInvalidArguments
		}
		object, ok := args[0].(MovingObject)
		if !ok {
			return nil, ErrInvalidArguments
		}
		return Move{Object: object}, nil
	})
	register, err := ioc.Resolve[Command](session, "IoC.Register", "game.move", factory)
	if err != nil {
		return err
	}
	if err := register.Execute(); err != nil {
		return err
	}
	move, err := ioc.Resolve[Command](session, "game.move", torpedo)
	if err != nil {
		return err
	}
	return move.Execute()
}
```

Для создания именованной области получают и исполняют команду `Scopes.New`, для выбора области в сессии - `Scopes.Current`. В дочерней области можно зарегистрировать тот же ключ с другой фабрикой. Поиск идет от выбранной области к родительской и корню.

В Go нет аналога C# `ThreadLocal`, подходящего как скрытая текущая область горутины. Поэтому каждому независимому сценарию передается своя `ScopeSession`; один контейнер и его регистрации могут использоваться параллельно. Мьютексы защищают карты, а фабрика вызывается вне блокировки. Тесты проверяют независимость 24 сессий и конкурентную регистрацию в одной области; `go test -race` проходит локально и в CI. Сессию не следует разделять между сценариями, которым нужны разные текущие области.

## Занятие 13: генерация адаптеров

`go generate ./...` запускает `cmd/adaptergen` для интерфейсов `MovingObject`, `RotatingObject` и `FinishingObject`. Генератор читает объявление интерфейса через `go/parser` и создает обычный Go-код. Созданные файлы включены в репозиторий; `go build` сам не запускает генератор. CI повторяет генерацию и проверяет, что файлы не изменились. Это перенос идеи ДЗ на этап сборки Go вместо компиляции C#-кода во время работы игры.

Метод с результатом `(T, error)` вызывает `Resolve[T]`. Метод с результатом `error` получает `Command` и исполняет его. Имена ключей выводятся из контракта: `Position()` использует `MovingObject:position.get`, `SetPosition(Vector)` использует `MovingObject:position.set`, а `Finish() error` использует `FinishingObject:finish.call`. Генератор явно отклоняет интерфейсы со встроенными методами, вариадическими аргументами и другими формами результата. При расширении контракта сначала нужно определить семантику вызова и ошибки, затем расширить генератор.

Один ключ `Adapter` принимает `reflect.TypeFor[MovingObject]()` и объект. Ниже часть настройки, где `session` и `object` уже созданы вызывающим кодом:

```go
ioc := NewIoC()
registry := NewAdapterRegistry()
if err := RegisterMovingObjectAdapter(registry); err != nil {
    return err
}
if err := registry.Install(ioc, nil); err != nil {
    return err
}
moving, err := ioc.Resolve[MovingObject](session, "Adapter", reflect.TypeFor[MovingObject](), object)
```

Здесь `session` может быть `nil` для корневой области. Перед первым вызовом `Position`, `Velocity` или `SetPosition` нужно зарегистрировать соответствующие фабрики по приведенным ключам. Для сеттеров фабрика возвращает `Command`. Адаптер получает сессию именно вызвавшего `Resolve`, поэтому регистрация `Adapter` в корне не мешает дочерней области переопределять поведение. `ContextFactory` добавлена для этого случая; прежний тип `Factory` продолжает работать.

Тесты проводят созданные адаптеры через прежние `Move` и `Rotate`, проверяют метод `Finish`, выбор области и ошибки регистрации и разрешения. Генератор проверяется отдельно на интерфейсе с импортированным типом, возвращающим значение сеттером и отклоняемыми сигнатурами.

## Занятие 17: несколько работников и остановка

`NewCommandWorker` создает одного исполнителя с собственной потокобезопасной FIFO-очередью. Производители могут вызывать `Enqueue` одновременно. `StartWorker.Execute()` запускает горутину; канал `Started()` подтверждает вход в рабочий цикл. Когда очередь пуста, работник ждет на `sync.Cond` и просыпается при новой команде или остановке. У нескольких работников очереди независимы. Старые `CommandQueue` и `Processor` сохранены для прежнего однопоточного сценария.

`HardStopWorker` закрывает прием новых команд и отбрасывает ожидающие, `SoftStopWorker` закрывает прием и исполняет все ранее принятые команды. Оба реализуют прежний `Command`, поэтому их можно поместить в очередь целевого работника. `StartWorker` нужно исполнить извне его собственной очереди. Остановка не прерывает команду, которая уже выполняется: `HardStop` возвращается сразу, а `Done()` закрывается после выхода рабочего цикла. Не вызывайте ожидание `Done()` из команды этого же работника.

Паника внутри команды превращается в `error` на границе `executeSafely`; цикл продолжает работу. `Failures()` возвращает копию накопленных ошибок. Этот список не ограничен по размеру и подходит для учебной задачи, а не для длительного сервера без отдельной политики ошибок. Потокобезопасность очереди не защищает состояние объекта, если один `Ship` одновременно меняют команды разных работников.

Тесты проверяют запуск без `Sleep`, пробуждение пустого работника, оба режима остановки, продолжение после ошибки и паники, независимые очереди, 50 конкурентных производителей и исполнение прежнего `Move`. Проверки: `go build ./...`, `go vet ./...`, `go test -race ./...`.

## Занятие 19: входящие сообщения агентов

`GameEndpoint` реализует `http.Handler` для `POST /commands`. Он принимает JSON с постоянным конвертом:

```json
{"game_id":"game-a","object_id":"ship-1","operation_id":"move","args":{}}
```

Для прежних локальных упражнений endpoint создается через `NewGameEndpoint(games)`. Для сетевого игрового сервера нужен `NewAuthorizedGameEndpoint(games, verifier, owners)` с проверкой JWT и владельца корабля; подробности в [документе ДЗ 25](auth-service.md). Любой из вариантов подключается через `mux.Handle("/commands", endpoint)`. `GameConfig` получает работника, IoC, объекты игры и соответствие публичных операций доверенным ключам; перед приемом запросов работника запускают через `Start()`.

`game_id` выбирает игру и ее `CommandWorker`. Endpoint ставит в его очередь `InterpretCommand`. Эта команда находит объект внутри выбранной игры, сопоставляет публичный `operation_id` с доверенным ключом IoC, создает игровую команду и ставит ее на исполнение. Фабрика операции получает объект и `json.RawMessage` с `args`, поэтому добавление нового правила требует новой фабрики и записи в `GameConfig.Operations`, а не изменения HTTP-обработчика. Внешняя строка никогда не передается в IoC как ключ без проверки по списку разрешенных операций.

`NewGame` и `NewGameEndpoint` копируют карты конфигурации. После сборки игры не переключайте ее `ScopeSession` и не регистрируйте новые фабрики во время обработки сообщений. Один объект должен принадлежать одному работнику или защищать свое состояние отдельно. Уже принятая `InterpretCommand` ставит свое действие перед следующим входящим сообщением; `SoftStop` исполняет такое продолжение, а `HardStop` отбрасывает ожидающие команды по прежнему контракту.

`202 Accepted` означает только постановку команды во внутреннюю очередь. Очередь находится в памяти и не переживает рестарт. Результат интерпретации и выполнения доступен локально через `Worker.Failures()`, но отдельного API статуса для агента нет. Защищенный вариант endpoint проверяет личность по токену и право на корабль; для реальных агентов дополнительно потребуются политика повторной доставки и сохранение результата. ДЗ не запускает игровой сервер с публичным портом.

Проверены маршрутизация между играми, существующая `Move`, новая операция через конфигурацию IoC, запрет прямого вызова произвольного ключа, ошибки HTTP/JSON, порядок действий и 80 одновременных запросов. Для ДЗ 25 дополнительно проверены выдача токена только участнику, подпись, срок, игра и владение кораблем. `go test -race ./...`, `go vet ./...` и `go build ./...` проходят.

## Занятие 32: интерпретация приказов

Общий `InterpretCommand` и защищенный endpoint уже существовали. `RegisterShipOrderOperations(ioc, session)` добавляет три фабрики IoC и возвращает карту публичных операций для `GameConfig.Operations`: `StartMove`, `StopMove`, `Shoot`. Вызывайте регистрацию при сборке игры до запуска работника. Если она завершилась ошибкой, ранее зарегистрированные фабрики остаются в области; не продолжайте запуск с частично собранной конфигурацией. К возвращенной карте можно добавить другую операцию и ее доверенный ключ IoC без изменения интерпретатора.

`StartMove` принимает `{"initialVelocity":2}` и задает положительную скалярную скорость `Ship`; следующий `Move` сдвигает корабль на один игровой шаг. `StopMove` принимает `{}` и задает скорость ноль без смены направления. `Shoot` принимает `{}` и вызывает `Fire()` у объекта. `ArmedShip` копирует исходный `Ship` и получает эффект выстрела через функцию при сборке, поэтому правило о снаряде или боезапасе не находится в JSON-интерпретаторе. Для объектов без нужной способности фабрика возвращает ошибку.

Пример приказа после сборки игры с `NewAuthorizedGameEndpoint`:

```json
{"game_id":"game-1","object_id":"ship-548","operation_id":"StartMove","args":{"initialVelocity":2}}
```

Токен игрока проверяется до постановки приказа в очередь, его `sub` должен совпадать с владельцем `object_id`. Другой игрок получает `403`, игра и объект не меняются. `202` подтверждает только прием в очередь: ошибка параметров конкретной операции или выстрела появится позже в `Worker.Failures()`. Тест проверяет последовательность `StartMove -> Move -> StopMove -> Move -> Shoot`, запрет чужих приказов и отсутствие изменения состояния при неправильных параметрах.
