# Космическая битва на Go

Учебная реализация заданий OTUS. Занятие 7 добавило движение и поворот, занятие 8 расширило код очередью и обработкой ошибок, занятие 9 добавляет макрокоманды и расход топлива. Прежние `Move`, `Rotate` и рабочий цикл очереди сохранены. В OTUS прежние сдачи занятий 7 и 9 уже имеют статус «принято, 10 баллов»; этот Go-код туда не отправлялся.

## Запуск

Из каталога проекта:

```sh
go build ./...
go test ./...
go vet ./...
```

В CI выполняются те же проверки. Используется стандартная библиотека Go без внешних зависимостей.

## Контракт

`Move{Object: object}.Execute()` читает положение и мгновенную скорость, складывает векторы и записывает новое положение. Операция не меняет скорость и не деформирует объект. Ошибка любого чтения или записи возвращается вызывающему коду с указанием этапа; исходная ошибка доступна через `errors.Is`. При ошибке чтения или нечисловом результате запись не вызывается.

`Rotate{Object: object}.Execute()` читает направление и угловую скорость, поворачивает на целое число секторов и записывает новое направление. Сектор нормализуется по кругу, включая отрицательные повороты. `Direction` создается через `NewDirection(index, sectors)` с `sectors > 0`. Нулевое значение `Direction` недопустимо.

В Go нет классов: отдельные операции оформлены структурами `Move` и `Rotate` с методом `Execute`. Интерфейсы `MovingObject` и `RotatingObject` содержат только операции, нужные соответствующей команде. `Ship` реализует оба интерфейса; `Torpedo` реализует только движение. Компилятор проверяет это через присваивания в конце файлов моделей.

`Ship` хранит не вектор скорости, а неотрицательную скалярную скорость и дискретное направление. Метод `Velocity()` вычисляет `speed * (cos(angle), sin(angle))`, где `angle = 2π * index / sectors`. Поэтому поворот влияет на следующий шаг движения. `Torpedo` хранит вектор скорости напрямую; код `Move` от этого не меняется.

Ограничения игрового поля можно разместить в `SetPosition` конкретного объекта или адаптера. Если новое положение запрещено, метод возвращает ошибку, а `Move` передает ее вызывающему коду. Тест `write position` проверяет этот путь. Это не реализует всю игровую механику: столкновения, победа флотилии, Player и Агент находятся за пределами задания на движение.

## Занятие 8: очередь и обработка ошибок

`Move` и `Rotate` теперь выполняются через общий интерфейс `Command`. `Processor` извлекает команды из FIFO-очереди и передает сбой первому подходящему `ErrorRule`, которое может учитывать и тип команды, и значение `error`. Обычные ошибки возвращаются как `error`; `panic` преобразуется в ошибку только на границе рабочего цикла. Если правило не найдено, ошибка возвращается вызывающему коду.

`LogFailure` пишет тип команды и сообщение ошибки в переданный `io.Writer`. `Retry` и `RetryTwice` выполняют исходную команду повторно. Обработчики `EnqueueLog` и `EnqueueRetry` только добавляют команды в очередь. `RetryOnceRules` дает одну повторную попытку и затем журнал; `RetryTwiceRules` дает две повторные попытки и затем журнал. Ошибка записи журнала не повторяется бесконечно. Тесты проверяют оба сценария, выбор по обернутой ошибке, FIFO, восстановление после `panic` и исполнение старой команды движения в новом цикле.

Повтор любой команды допустим здесь как требование ДЗ. Для реального сервера потребуются классификация временных ошибок и гарантия безопасного повторного выполнения после частичного действия. Очередь сейчас рассчитана на одного рабочего.

## Занятие 9: макрокоманды и топливо

`MacroCommand` принимает последовательность `Command`, исполняет ее по порядку и останавливается на первой ошибке. `CommandError` сохраняет номер неудачного шага и исходную причину через `Unwrap`, поэтому работают `errors.As` и `errors.Is`.

`NewMoveWithFuel` строит цепочку `CheckFuel -> Move -> BurnFuel`. Нехватка топлива останавливает движение. Ошибка `Move` не запускает списание. `BurnFuel` проверяет остаток и при отдельном вызове не допускает отрицательного запаса. `FueledShip` использует правила прежнего `Ship`, хранит запас топлива и собственный вектор скорости. При создании он копирует исходный `Ship`, чтобы дальнейшие изменения через старый указатель не нарушили его состояние.

`NewRotateWithVelocity` строит цепочку `Rotate -> ChangeVelocity`. `ChangeVelocity` обновляет вектор только у объекта с контрактом `VelocityAdjustable`. Для неподвижной поворачиваемой башни это допустимое пустое действие. Прежний `Ship` сам вычисляет вектор из направления, поэтому после поворота его скорость уже корректна. У `FueledShip` вектор хранится, и составная команда пересчитывает его явно.

Макрокоманда не выполняет откат. Если `BurnFuel` вернет ошибку, положение уже может быть изменено. Поэтому общие правила повтора из занятия 8 нельзя применять к ней без проверки безопасности повторного выполнения. В тестах проверены порядок шагов, остановка на ошибке, нехватка и точный остаток топлива, связь поворота со следующим движением, объект без движения и сохранение поведения прежнего `Ship`.
